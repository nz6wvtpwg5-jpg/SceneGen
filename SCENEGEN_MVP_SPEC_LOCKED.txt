================================================================================
CORE PRINCIPLES
================================================================================
- Exactly TWO entity types exist: Artist and Promoter.
- A signed-in user may administrate ONE entity only (Artist OR Promoter).
- Entities (not users) are the professional identities throughout the app.
- Chat, contacts, shows, tours all operate at the ENTITY level.
- Touring is an ARTIST-ONLY feature.
- No billing, no Stripe, no paid tiers in MVP.
- No additional chat types in MVP (single entity-to-entity chat only).

================================================================================
IDENTITY & OWNERSHIP (IMPORTANT CORRECTION)
================================================================================
❌ DO NOT add new user fields such as `user.administratorOf`.
✅ Ownership is derived solely by querying: entity.administratorId === userId

This avoids multiple sources of truth.

Rules:
- A user may only be administratorId of ONE entity.
- Backend blocks creation if user already owns an entity.
- Frontend hides onboarding once an entity exists.

Implementation:
// Check if user owns an entity (backend)
const existingEntity = await db.query(
  "SELECT id FROM entities WHERE administratorId = ?",
  [userId]
);
if (existingEntity) {
  return { error: "User already owns an entity", status: 409 };
}

// Check if user owns an entity (frontend)
const userEntities = await fetch('/api/user/entities');
const ownedEntity = userEntities.find(e => e.administratorId === userId);
if (ownedEntity) {
  // Hide onboarding, disable creation
}

================================================================================
ONBOARDING / ENTITY CREATION
================================================================================
- If signed in and user does NOT administrate an entity → redirect to onboarding.
- Onboarding allows creation of:
  - Artist OR Promoter (never both).
- After creation:
  - Entity becomes activeProfile.
  - Onboarding is permanently disabled.

Invite-driven onboarding:
- Visiting /invite/{token} with no entity:
  - User must create an entity.
  - Entity type is enforced by invite.
- On completion:
  - Invite marked accepted.
  - Contact relationship created.
  - Trial access granted.
  - If show invite → entity linked to show.

CONTACTS (ENTITY ↔ ENTITY)
================================================================================
Contact Model:
{
  "id": "uuid",
  "entityId1": "uuid",
  "entityId2": "uuid",
  "status": "pending | accepted",
  "initiatedBy": "entityId",
  "createdAt": "ISO 8601",
  "acceptedAt": "ISO 8601 | null"
}

Rules:
- Contacts exist ONLY between entities.
- Status: pending / accepted.
- Contacts are REQUIRED for general chat.
- Contacts are NOT required to create shows or send show invites.

Contacts can be created via:
1) Manual selection of existing entity.
2) Invite URL.
3) Automatically when a show invite is accepted.

================================================================================
INVITES (DYNAMIC URLS)
================================================================================
Invite types:
- contact_invite
- show_invite

Invite Model:
{
  "token": "uuid",
  "invitingEntityId": "uuid",
  "requiredEntityType": "artist | promoter | any",
  "inviteType": "contact_invite | show_invite",
  "showId": "uuid | null",
  "expiresAt": "ISO 8601",
  "acceptedAt": "ISO 8601 | null",
  "status": "pending | accepted | expired"
}

Invite flow:
1. Visit /invite/{token}
2. Authenticate if required
3. If no entity → onboarding (type enforced)
4. Accept invite:
   - Contact created
   - Trial access granted
   - If show invite → link entity to show

Validation:
- Expired or reused invites are rejected.

================================================================================
TRIAL ACCESS (MINIMAL)
================================================================================
- Entities created via invite receive time-limited trial access.
- Trial gating is simple:
  - If trial expired → restrict creation of new shows or tours.

Implementation:
- Entity has trialExpiresAt field
- Middleware checks: if (now > entity.trialExpiresAt) { restrict }
- NO billing logic in MVP
- NO Stripe integration in MVP
- NO 402 errors
- Use standard 403 with clear UI messaging:
  "Your trial has expired. Upgrade to continue creating shows."

SHOWS (DAY SHEET BASED)
================================================================================
Show Model:
{
  "id": "uuid",
  "artistEntityId": "uuid",
  "promoterEntityId": "uuid",
  "tourId": "uuid | null",
  "createdBy": "entityId",
  "status": "draft | pending_invite | pending_acceptance | confirmed | cancelled",
  "createdAt": "ISO 8601",
  "updatedAt": "ISO 8601",

  // Day Sheet Fields
  "showDate": "ISO 8601",
  "venueName": "string",
  "venueAddress": "string",
  "venueCity": "string",
  "venueState": "string",
  "venueCountry": "string",
  "venueCapacity": "number | null",
  "doorsTime": "string",
  "showTime": "string",
  "setLength": "string",
  "guarantee": "number | null",
  "dealType": "guarantee | door_split | guarantee_vs_split",
  "doorSplitPercentage": "number | null",
  "advanceTicketPrice": "number | null",
  "doorTicketPrice": "number | null",
  "notes": "string | null",
  "technicalRequirements": "string | null",
  "contactName": "string",
  "contactPhone": "string",
  "contactEmail": "string"
}

Rules:
- Every show involves exactly ONE Artist and ONE Promoter.
- Shows may be:
  - Standalone (tourId = null)
  - Part of a tour (tourId = uuid)

Show lifecycle:
- draft → pending_invite → pending_acceptance → confirmed
- Any status → cancelled

Show creation flow:
1. Creator (Artist or Promoter) starts Create Show
2. Select counterparty:
   - Existing entity (from contacts or search)
   - OR invite via URL (generates show_invite)
3. Artist is ALWAYS asked:
   - Standalone show
   - Part of a tour
     - Select existing tour (dropdown)
     - OR create new tour inline (modal)
4. Fill Day Sheet fields (venue, date, deal, etc.)
5. Submit:
   - Existing counterparty → status = pending_acceptance
   - Invited counterparty → status = pending_invite

MVP SIMPLIFICATION (Editing):
- Creator can edit show freely while status = draft
- After confirmed:
  - Edits are allowed
  - Edits are logged (audit trail)
  - ❌ NO reconfirmation workflow in MVP
  - ❌ NO version history in MVP

Cancellation:
- Either party can cancel at any time
- Status → cancelled
- Show remains in database (for history)

Ably Integration:

Flow:

2. Either entity can start conversation
3. ConversationId created
4. Both entities subscribe to Ably channel
5. Real-time messages flow through channel
6. Message history fetched from backend

================================================================================
TOURS (DATA MODEL)
================================================================================
Tour Model:
{
  "id": "uuid",
  "artistEntityId": "uuid",       // Owning artist
  "name": "string",               // e.g., "West Coast Tour 2026"
  "notes": "string | null",
  "startDate": "ISO 8601",        // Derived from shows
  "endDate": "ISO 8601",          // Derived from shows
  "createdAt": "ISO 8601",
  "updatedAt": "ISO 8601"
}

Rules:
- A tour belongs to ONE Artist entity
- A show may belong to ONE tour or none (show.tourId)
- Tour dates are DERIVED from associated shows:
  - startDate = MIN(show.showDate) for shows in tour
  - endDate = MAX(show.showDate) for shows in tour
- Dates auto-update when shows added/removed

❌ NO manual date overrides in MVP

UI Options:

function requireArtistEntity(req, res, next) {
  const entity = req.activeEntity;
  if (!entity || entity.entityType !== 'artist') {
    return res.status(403).json({ error: 'Artist entities only' });
  }
  next();
}

================================================================================
EDGE CASES & VALIDATIONS
================================================================================
1. User tries to create second entity:
   → Backend returns 409 Conflict
   → Message: "You already own an entity"

2. Promoter tries to access /touring:
   → Frontend hides link
   → Backend returns 403 Forbidden

3. Expired trial tries to create show:
   → Backend returns 403 Forbidden
   → Message: "Your trial has expired. Contact support to continue."

4. Invite accepted by wrong entity type:
   → Validation fails during onboarding
   → Message: "This invite requires a [type] account"

5. Show added to tour while already in tour:
   → Warning modal: "This show is part of [Tour A]. Move to [Tour B]?"
   → Options: Cancel / Move

6. Show cancelled:
   → Status → cancelled
   → Show remains in database
   → No notifications in MVP

7. Tour deleted:
   → All shows.tourId set to null (become standalone)
   → Confirmation warning: "N shows will become standalone"

8. User with no entity visits /invite/{token}:
   → Redirected to sign in (if not authenticated)
   → Then redirected to onboarding (type enforced)
   → On completion: invite accepted, contact created

9. Expired invite visited:
   → Error: "This invite has expired"
   → No recovery in MVP

10. Contact already exists when accepting invite:
    → Skip contact creation
    → Still mark invite as accepted
    → Still grant trial access (if applicable)
