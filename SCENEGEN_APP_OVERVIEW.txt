1. INTRODUCTION & PURPOSE
================================================================================

WHAT IS SCENEGEN?
SceneGen is a touring and show management platform that connects artists and 
promoters. It facilitates collaboration on booking shows, organizing tours, 
and managing contacts in the live music industry.

TARGET USERS:
- Artists: Musicians/bands who tour and perform live shows
- Promoters: Venue operators/booking agents who host shows

KEY PROBLEM SOLVED:
Streamlines the complex process of booking tours, managing multiple shows, 
coordinating between artists and promoters, and maintaining professional 
relationships in the music industry.

MVP SCOPE:
The current implementation includes:
✓ User authentication and entity ownership
✓ Artist/Promoter profile management
✓ Contact networking system
✓ Show creation and management
✓ Tour organization (artist-only)
✓ Interactive touring map (artist-only)
✓ Invite system for onboarding
✓ Bulk operations on shows
✓ Advanced filtering and search

2. SYSTEM ARCHITECTURE
================================================================================

ARCHITECTURE PATTERN:
- Frontend: Next.js 14 (App Router) with React 18
- API Layer: Next.js API Routes (Proxy Pattern)
- Authentication: NextAuth.js with JWT tokens
- State Management: Zustand (lightweight, hook-based)
- Styling: Tailwind CSS + shadcn/ui components
- Map Integration: Leaflet + react-leaflet

ARCHITECTURAL DECISIONS:

A) API PROXY PATTERN
   All frontend API calls go through Next.js API routes in /app/api/
   
   Flow:
   Frontend Component → API Route (src/app/api/*) → Backend API
   
   Benefits:
   - Keeps backend URLs hidden from client
   - Centralized auth token handling
   - Easy to mock during development
   - CORS management
   - Request/response transformation

B) SERVER-SIDE RENDERING (SSR)
   Next.js App Router provides:
   - Server components by default
   - Client components marked with "use client"
   - Automatic code splitting
   - Optimized loading

C) COMPONENT-DRIVEN ARCHITECTURE
   - Atomic design principles
   - Reusable UI components in /components/ui/
   - Feature-specific components in /components/[feature]/
   - Separation of concerns

D) HOOK-BASED STATE MANAGEMENT
   - Custom hooks for each feature (useShows, useTours, etc.)
   - Zustand for global state (user profile)
   - React hooks for local state
   - No Redux complexity

4. AUTHENTICATION & USER FLOW
================================================================================

AUTHENTICATION SYSTEM:

A) SETUP (src/auth.ts)
   - NextAuth.js configured with JWT strategy
   - Session stored in secure HTTP-only cookies
   - Token includes: user ID, email, access token

B) AUTH FLOW:
   1. User logs in (external auth provider or custom)
   2. NextAuth creates session with JWT
   3. Session stored in cookie
   4. Access token passed to backend in API calls

C) SESSION MANAGEMENT:
   - SessionProviderWrapper wraps entire app
   - useSession() hook provides session data anywhere
   - Middleware checks auth on protected routes

D) PROTECTED ROUTES:
   Middleware (src/middleware.ts) protects:
   - /dashboard
   - /shows
   - /contacts
   - /tours
   - /touring
   - /profile
   
   Redirects to /api/auth/signin if not authenticated

E) TOKEN HANDLING:
   All API proxy routes extract token from session:
   ```typescript
   const session = await getServerSession(authOptions);
   const token = session?.access_token;
   
   fetch(backendUrl, {
     headers: {
       'Authorization': `Bearer ${token}`
     }
   })
   ```

5. CORE ENTITIES & DATA MODELS
================================================================================

A) USER
   - id: string (UUID)
   - email: string
   - name: string
   - Role: User can own ONE entity (artist OR promoter)

B) ENTITY
   - id: string (UUID)
   - administratorId: string (user ID)
   - entityType: 'artist' | 'promoter'
   - name: string
   - city: string
   - state: string
   - country: string
   - latitude?: number
   - longitude?: number
   - bio?: string
   - genres?: string[]
   - memberNames?: string[]
   - profileImageUrl?: string
   - headerImageUrl?: string
   - trialExpiry?: string (ISO date)
   
   Relationship: User 1:1 Entity (enforced)

C) CONTACT
   - id: string (UUID)
   - entityId1: string (entity ID)
   - entityId2: string (entity ID)
   - status: 'pending' | 'accepted'
   - initiatedBy: string (entity ID)
   - createdAt: string (ISO date)
   - acceptedAt?: string (ISO date)
   
   Relationship: Entity M:N Entity (through contacts)

D) SHOW
   - id: string (UUID)
   - artistEntityId: string
   - promoterEntityId: string
   - tourId?: string (nullable)
   - createdBy: string (entity ID)
   - venueName: string
   - venueCity: string
   - venueState: string
   - venueCountry: string
   - showDate: string (ISO date)
   - showTime: string (HH:MM)
   - doorsTime: string (HH:MM)
   - setLength: string
   - guarantee?: number
   - dealType: 'guarantee' | 'door_split' | 'guarantee_vs_percentage' | 
               'flat_fee' | 'other'
   - status: 'draft' | 'pending_invite' | 'pending_acceptance' | 
             'confirmed' | 'cancelled'
   - notes?: string
   - createdAt: string
   - updatedAt: string
   
   Relationships:
   - Artist Entity 1:M Shows
   - Promoter Entity 1:M Shows
   - Tour 1:M Shows (optional)

E) TOUR (Artist-Only)
   - id: string (UUID)
   - artistEntityId: string
   - name: string
   - notes?: string
   - startDate: string (computed from shows)
   - endDate: string (computed from shows)
   - createdAt: string
   - updatedAt: string
   
   Relationship: Artist Entity 1:M Tours

F) INVITE
   - id: string (UUID)
   - token: string (unique)
   - inviteType: 'general' | 'show_invite'
   - inviterEntityId: string
   - recipientEmail: string
   - showId?: string (for show invites)
   - status: 'pending' | 'accepted' | 'expired'
   - expiresAt: string (ISO date)
   - createdAt: string
   
   Purpose: Onboarding new users with context

AUTHENTICATION FLOW IN API ROUTES:

Every protected API route follows this pattern:

```typescript
import { getServerSession } from 'next-auth';
import { authOptions } from '@/auth';
import { NextRequest, NextResponse } from 'next/server';

export async function GET(request: NextRequest) {
  // 1. Get session
  const session = await getServerSession(authOptions);
  
  // 2. Check auth
  if (!session?.access_token) {
    return NextResponse.json(
      { error: 'Unauthorized' },
      { status: 401 }
    );
  }
  
  // 3. Extract token
  const token = session.access_token;
  
  // 4. Call backend
  const response = await fetch('BACKEND_URL/endpoint', {
    headers: {
      'Authorization': `Bearer ${token}`,
      'Content-Type': 'application/json'
    }
  });
  
  // 5. Handle response
  if (!response.ok) {
    return NextResponse.json(
      { error: 'Backend error' },
      { status: response.status }
    );
  }
  
  // 6. Return data
  const data = await response.json();
  return NextResponse.json(data);
}
```


REQUEST/RESPONSE PATTERNS:

CREATE (POST):
Request:
  - Body: JSON with entity data
  - Headers: Authorization Bearer token
Response:
  - 201 Created: { id, ...entity }
  - 400 Bad Request: { error: "message" }
  - 401 Unauthorized: { error: "Unauthorized" }
  - 409 Conflict: { error: "Already exists" }

READ (GET):
Request:
  - Query params for filtering
  - Headers: Authorization Bearer token
Response:
  - 200 OK: { data } or [array]
  - 401 Unauthorized
  - 404 Not Found

UPDATE (PATCH):
Request:
  - Body: Partial entity data
  - Headers: Authorization Bearer token
Response:
  - 200 OK: { ...updated entity }
  - 400 Bad Request
  - 401 Unauthorized
  - 404 Not Found

DELETE:
Request:
  - Headers: Authorization Bearer token
Response:
  - 200 OK: { success: true }
  - 401 Unauthorized
  - 404 Not Found

ERROR HANDLING IN API ROUTES:

Standard error response format:

ERROR HANDLING STRATEGY:

LEVEL 1: API ROUTE ERRORS
- Try/catch in every API route
- Return appropriate HTTP status code
- Return JSON with error message
- Log errors to console (future: error tracking service)

Example:
```typescript
try {
  const data = await fetchFromBackend();
  return NextResponse.json(data);
} catch (error) {
  console.error('API Error:', error);
  return NextResponse.json(
    { error: 'Failed to fetch data' },
    { status: 500 }
  );
}
```

LEVEL 2: HOOK ERRORS
- Try/catch in all async operations
- Set error state
- Return error to component

Example:
```typescript
const [error, setError] = useState<string | null>(null);

const fetchShows = async () => {
  try {
    setError(null);
    const response = await fetch('/api/shows');
    if (!response.ok) throw new Error('Failed to fetch');
    return await response.json();
  } catch (err: any) {
    setError(err.message);
    throw err;
  }
};
```

LEVEL 3: COMPONENT ERRORS
- Try/catch around async operations
- Display error via toast notification
- Optionally display inline error

Example:
```typescript
const handleSubmit = async () => {
  try {
    await createShow(formData);
    toast.success('Show created successfully!');
  } catch (err: any) {
    toast.error(err.message || 'Failed to create show');

};
```

/src/app/[route]/
- Next.js file-based routing

CODING STANDARDS:

TypeScript:
- Use strict mode
- Define types for all props
- Avoid 'any' type
- Use interfaces for objects
- Export types from separate files

React:
- Functional components only
- Use hooks (no class components)
- Props destructuring
- Named exports for components
- Default export for pages

Naming:
- Components: PascalCase (UserProfile.tsx)
- Hooks: camelCase with 'use' prefix (useShows.ts)
- Types: PascalCase (Show, Tour)
- Files: Match component name
- API routes: lowercase (route.ts)

Imports:
- React imports first
- Next.js imports second
- Third-party imports third
- Local imports last
- Group by type (types, hooks, components)

Comments:
- JSDoc for complex functions
- Inline comments for tricky logic
- Component purpose at top
- BUILD_PLAN references
