Issue: Map not auto-zooming to fit all waypoints despite correct fitBounds implementation

PROBLEM STATEMENT
-----------------
The tour map is displaying with excessive zoom (appears zoomed in too much), preventing users
from seeing all show markers/waypoints across the United States. Despite implementing the
Google Maps API fitBounds() method with correct bounds calculations, the map remains zoomed
in and does not show the full geographical spread of the tour.

-----------------

SUSPECTED ROOT CAUSES
---------------------

Hypothesis #1: Timing Issue with Directions API
The most likely cause is that the Directions API route calculation is completing AFTER
our fitBounds call, and the Directions service is then applying its own zoom/bounds
to fit the route. This would override our custom fitBounds settings.

Evidence supporting this:
- fitBounds is confirmed to be called correctly
- Bounds calculation is correct
- The map does display the route, suggesting Directions API is working
- Directions API typically applies its own viewport when rendering routes

Hypothesis #2: Map Animation/Transition Timing
The fitBounds call might be executing before the map is fully initialized or before
all show markers are rendered, causing the bounds to be calculated but then reset
by subsequent map operations.

Hypothesis #3: Multiple fitBounds Calls Conflicting
Calling fitBounds twice (once on load, once after route) might be causing conflicts,
where the second call doesn't complete due to the first call still animating.

Hypothesis #4: DirectionsRenderer Override
The DirectionsRenderer component (used to display the route on the map) might have
default behavior that automatically sets the map viewport to fit the route, overriding
our custom fitBounds calls.

NEXT STEPS TO RESOLVE
----------------------

Priority 1: DirectionsRenderer Investigation
- Check if DirectionsRenderer has a 'preserveViewport' option
- This option (if it exists) would prevent DirectionsRenderer from auto-fitting the viewport
- Implementation: Add { preserveViewport: true } to DirectionsRenderer options

Priority 2: Timing Adjustment
- Move fitBounds call to execute AFTER DirectionsRenderer completes
- Use DirectionsRenderer callback or promise resolution
- Add delay/setTimeout as temporary test to confirm timing hypothesis

Priority 3: Single fitBounds Strategy
- Remove the initial fitBounds call on map load
- Only call fitBounds once, after the route is fully rendered
- This eliminates potential conflicts from multiple calls

Priority 4: Manual Zoom/Center as Fallback
- If fitBounds continues to fail, implement manual zoom calculation
- Calculate center point of all coordinates
- Set explicit zoom level based on geographical spread
- Use map.setCenter() and map.setZoom() instead of fitBounds

CONCLUSION
----------
The issue is NOT with data loading, coordinate validity, or bounds calculation. All
these aspects have been verified and are working correctly. The problem lies in the
interaction between our custom fitBounds implementation and the Google Maps
DirectionsRenderer component, likely due to timing or the DirectionsRenderer
automatically setting its own viewport.

The most promising solution is to add preserveViewport option to DirectionsRenderer
or to ensure fitBounds is called after the route rendering completes and potentially
overrides any viewport changes made by DirectionsRenderer.
