CORE PRINCIPLES
================================================================================
- There are exactly two entity types: Artist and Promoter.
- A signed-in user may only be the administrator of ONE entity (Artist OR Promoter).
- Entities (not raw users) are the professional identities used across the app.
- Artists and Promoters communicate via chat after entity connections are established.
- Growth and workflow are driven by invites, shows, tours, and contacts.

IDENTITY & OWNERSHIP RULES
================================================================================
User-to-Entity Relationships:
- A user may be linked to multiple entities as a member or admin, but:
  - A user may only be the administratorId of ONE entity (ever).
- Ownership = administratorId === userId.
- Enforced in backend (block duplicate creation) and frontend (disable onboarding button).

Permission Model:
┌─────────────────────────────────────────────────────────────────────────┐
│ ROLE         │ PERMISSIONS                                              │
├─────────────────────────────────────────────────────────────────────────┤
│ Administrator│ - Full control of entity profile                         │
│              │ - Create/edit/cancel shows                               │
│              │ - Manage contacts                                        │
│              │ - Start/manage chats                                     │
│              │ - Invite new members (artists only)                      │
│              │ - Delete entity                                          │
│              │ - Assign activeProfile in UI                             │
├─────────────────────────────────────────────────────────────────────────┤
│ Member       │ - View entity profile                                    │
│ (Artists only)│ - View shows (read-only)                                │
│              │ - View contacts (read-only)                              │
│              │ - Participate in entity chats (if invited to conversation)│
│              │ - Cannot modify entity                                   │
│              │ - Cannot create shows or contacts                        │
│              │ - Can switch to this entity as activeProfile            │
├─────────────────────────────────────────────────────────────────────────┤
│ User (no     │ - Must complete onboarding                               │
│ entity)      │ - Can accept invites                                     │
│              │ - Cannot access main app features                        │
└─────────────────────────────────────────────────────────────────────────┘

Notes:
- Promoter entities do NOT have members (business-only)
- Members can be added via invite or manual assignment by admin
- Members receive read-only access to entity context

ONBOARDING / ENTITY CREATION
================================================================================
Rules:
- If signed in and user does not administrate an entity → redirect to /onboarding.
- Onboarding allows creation of Artist OR Promoter (never both).
- After creation:
  - Entity becomes activeProfile.
  - User.administratorOf = entityId
  - Onboarding is permanently disabled for this user.

Invite-Driven Onboarding:
- If user visits invite URL and has no entity:
  - Onboarding enforces entity type from invite.
  - No choice given (e.g., "This invite requires a Promoter account").
- After entity creation via invite:
  - Invite marked as accepted
  - Contact relationship auto-created
  - Trial access granted
  - If show_invite: entity linked to show

Backend Enforcement:
- POST /api/artist/add checks: user.administratorOf === null
- POST /api/promoter/add checks: user.administratorOf === null
- Return 409 Conflict if user already owns entity

CONTACTS (ENTITY TO ENTITY)
================================================================================
Contact Model:
{
  "id": "uuid",
  "entityId1": "uuid",           // First entity in relationship
  "entityId2": "uuid",           // Second entity in relationship
  "status": "pending | accepted",
  "initiatedBy": "entityId",     // Who sent the request
  "createdAt": "ISO 8601",
  "acceptedAt": "ISO 8601 | null"
}

Rules:
- Contacts exist between entities, not users.
- Any entity type can connect with any other entity type:
  - Artist ↔ Promoter (primary use case)
  - Artist ↔ Artist (for support acts, collaborations)
  - Promoter ↔ Promoter (for co-promoted shows)
- Status: pending / accepted.
- Contacts are required for general chat (see Chat section).
- Contacts are NOT required to create shows or send show invites.

Contact Creation Methods:
1. Manual Selection:
   - Search for entity by name
   - Send contact request
   - Recipient accepts/rejects

2. Via Invite URL:
   - Generate contact_invite with token
   - Share URL
   - Recipient creates entity (if needed) → auto-connected

3. Auto-Created:
   - When show invite is accepted
   - When user accepts invite of any type

INVITES (DYNAMIC URLS)
================================================================================
Invite Types:
- contact_invite: Pure networking
- show_invite: Invite to specific show (creates contact + links to show)

Invite Model:
{
  "token": "uuid",
  "invitingEntityId": "uuid",
  "requiredEntityType": "artist | promoter | any",
  "inviteType": "contact_invite | show_invite",
  "showId": "uuid | null",       // Only for show_invite
  "recipientEmail": "string | null", // Optional hint
  "expiresAt": "ISO 8601",
  "acceptedAt": "ISO 8601 | null",
  "acceptedBy": "entityId | null",
  "createdAt": "ISO 8601",
  "status": "pending | accepted | expired | cancelled"
}

Invite Flow:
1. Entity A creates invite:
   - Specifies type (contact or show)
   - Specifies required entity type (artist / promoter / any)
   - Optionally provides email
   - Backend generates token, creates invite record

2. Recipient visits /invite/{token}:
   - If not authenticated → sign in/sign up
   - If authenticated but no entity:
     - Redirect to onboarding
     - Entity type selector disabled if invite requires specific type
   - If authenticated with entity:
     - Check entity type matches invite requirement
     - Accept invite → create contact + grant trial + link show (if applicable)

3. On completion:
   - Invite.status = accepted
   - Invite.acceptedBy = recipientEntityId
   - Contact created with status = accepted
   - Trial access granted to recipient entity
   - If show_invite: recipient entity linked to show as counterparty

Validation:
- Expired invites cannot be accepted
- Invites can only be accepted once
- Entity type must match requiredEntityType (if not "any")

TRIAL ACCESS
================================================================================
Rules:
- Entities created via invite receive time-limited trial access.
- Trial duration: 30 days from entity creation.
- After trial expires, entity moves to Free tier.

Free Tier Limits (post-trial):
- 1 active show (draft, pending, or confirmed)
- 5 total contacts
- No access to Touring features (artists)
- Basic chat (no file uploads, limited history)
- View-only access to analytics

Paid Tier (Subscription):
- Unlimited shows
- Unlimited contacts
- Full touring features
- Advanced chat (file uploads, full history)
- Analytics and insights
- Priority support

Middleware Enforcement:
- Check entity.trialExpiresAt vs. current date
- Check entity.subscriptionStatus (trial | free | paid)
- Return 402 Payment Required for restricted features
- Frontend shows upgrade prompts

SHOWS (DAY SHEET BASED)
================================================================================
Show Model:
{
  "id": "uuid",
  "artistEntityId": "uuid",
  "promoterEntityId": "uuid",
  "tourId": "uuid | null",
  "createdBy": "entityId",          // Who created the show
  "status": "draft | pending_invite | pending_acceptance | confirmed | cancelled",
  "createdAt": "ISO 8601",
  "updatedAt": "ISO 8601",
  "confirmedAt": "ISO 8601 | null",
  "cancelledAt": "ISO 8601 | null",
  "cancelledBy": "entityId | null",

  // Day Sheet Fields (mirror exactly)
  "showDate": "ISO 8601",
  "venueName": "string",
  "venueAddress": "string",
  "venueCity": "string",
  "venueState": "string",
  "venueCountry": "string",
  "venueCapacity": "number | null",
  "doorsTime": "string",            // e.g., "19:00"
  "showTime": "string",             // e.g., "20:00"
  "setLength": "string",            // e.g., "60 mins"
  "guarantee": "number | null",
  "dealType": "guarantee | door_split | guarantee_vs_split",
  "doorSplitPercentage": "number | null",
  "advanceTicketPrice": "number | null",
  "doorTicketPrice": "number | null",
  "notes": "string | null",
  "technicalRequirements": "string | null",
  "contactName": "string",          // Venue/promoter contact
  "contactPhone": "string",
  "contactEmail": "string"
}

Show Ownership Rules:
- Shows are co-owned by both Artist and Promoter entities.
- Both parties have equal rights to:
  - View the show
  - Propose edits (triggers re-confirmation)
  - Cancel the show
- Creator makes initial proposal (status = draft or pending_invite).
- Counterparty must confirm (status → confirmed).
- If either party cancels:
  - status → cancelled
  - cancelledBy records which entity cancelled

Show Status Lifecycle:
┌──────────────────────────────────────────────────────────────────────────┐
│ draft                                                                    │
│   ↓ (creator invites counterparty or selects existing entity)           │
│ pending_invite (if counterparty doesn't exist or not yet confirmed)     │
│   ↓ (invitee accepts invite)                                            │
│ pending_acceptance (counterparty entity exists, must confirm show)      │
│   ↓ (counterparty confirms)                                             │
│ confirmed                                                                │
│   ↓ (either party cancels)                                              │
│ cancelled [terminal state]                                              │
└──────────────────────────────────────────────────────────────────────────┘

Create Show Flow:
1. Creator (Artist or Promoter) initiates "Create Show"
2. Select counterparty:
   - Option A: Existing contact (entity picker)
   - Option B: Invite new [Artist/Promoter]
     - Choose entity type
     - Optionally provide email
     - Generate show_invite URL
3. Select tour context (Artists only):
   - Standalone show
   - Part of existing tour (dropdown)
   - Create new tour inline (modal)
4. Fill Day Sheet fields (venue, date, deal, etc.)
5. Submit:
   - If counterparty exists: status = pending_acceptance
   - If counterparty is invite: status = pending_invite

Edit Show:
- Either party can propose changes
- Triggers status → pending_acceptance (requires re-confirmation)
- Version history tracked (optional)

Cancel Show:
- Either party can cancel at any time
- Confirmation prompt: "Are you sure?"
- status → cancelled
- cancelledBy = current entity
- Notification sent to counterparty

CHAT (ENTITY-SCOPED)
================================================================================
Chat Architecture:
- Chat is entity-to-entity, not user-to-user.
- Two types of chat:
  1. General Chat: Requires accepted contact
  2. Show-Specific Chat: Available once show is created (any status)

General Chat:
- Only available between entities with contact.status = "accepted"
- Conversation model:
  {
    "conversationId": "uuid",
    "entityId1": "uuid",
    "entityId2": "uuid",
    "lastMessage": "string",
    "updatedAt": "ISO 8601",
    "participants": ["Entity Name 1", "Entity Name 2"]
  }
- Conversation ID maps to Ably channel
- Ably auth restricts channel access to entity participants

Show-Specific Chat:
- Available as soon as show is created (any status)
- Allows negotiation before formal contact acceptance
- Scoped to show context
- Conversation model:
  {
    "conversationId": "uuid",
    "showId": "uuid",
    "artistEntityId": "uuid",
    "promoterEntityId": "uuid",
    "lastMessage": "string",
    "updatedAt": "ISO 8601"
  }
- Separate from general entity-to-entity chat
- Deleted if show is cancelled (with warning)

Message Model:
{
  "messageId": "uuid",
  "conversationId": "uuid",
  "senderId": "userId",            // Which user sent (for display)
  "senderEntityId": "entityId",    // Which entity context
  "content": "string",
  "sentAt": "ISO 8601",
  "readBy": ["userId"]
}

Ably Integration:
- Channel naming:
  - General: `entity-chat:{conversationId}`
  - Show: `show-chat:{showId}`
- Auth endpoint: /api/chat/auth
- Validates user has access to entity in conversation
- Returns Ably token scoped to allowed channels

Chat UI:
- Sidebar: Conversations list (sorted by updatedAt)
- Main view: ChatBox (messages + input)
- Shows sender entity name (not user name)
- Avatars generated per entity
- Unread indicators
- Typing indicators (optional)

TOURS – DATA MODEL
================================================================================
Tour Model:
{
  "id": "uuid",
  "artistEntityId": "uuid",        // Owning artist
  "name": "string",                // e.g., "West Coast Winter Tour 2026"
  "notes": "string | null",
  "manualStartDate": "ISO 8601 | null",  // Manual override
  "manualEndDate": "ISO 8601 | null",    // Manual override
  "createdAt": "ISO 8601",
  "updatedAt": "ISO 8601"
}

Tour Dates Logic:
- Computed dates derived from associated shows:
  - computedStartDate = MIN(show.showDate) for shows in tour
  - computedEndDate = MAX(show.showDate) for shows in tour
- Display logic:
  - If manualStartDate is set → display manual
  - Else → display computedStartDate
  - Same for endDate
- Dates auto-update when shows added/removed (computed dates)
- Manual dates are optional overrides (for pre-tour planning)

Show-Tour Association:
- A show may belong to ONE tour or none (tourId field)
- Shows can be moved between tours
- Standalone shows have tourId = null

TOURING NAVIGATION
================================================================================
Route: /touring
Guards:
- Frontend: activeProfile.entityType === "artist"

Create Tour Modal:

- Submit:
  - POST /api/tours

SHOWS ↔ TOURS INTERACTION
================================================================================
During Create Show:
- Step: "Is this show part of a tour?"
  - Radio options:
    - Standalone show (tourId = null)
    - Part of existing tour (dropdown of artist's tours)
    - Create new tour (opens inline modal)
- If "Part of existing tour":
  - Tour preselected in show object
- If "Create new tour":
  - Modal opens
  - On submit: tour created, show.tourId = new tour ID

From Shows Page:
- Bulk selection mode:
  - Checkboxes on each show row
  - "N shows selected" indicator
  - Bulk actions toolbar appears
- Actions:
  - "Add to Tour" button
    - Opens modal
    - Options:
      - Select existing tour (dropdown)
      - Create new tour (inline)
  - "Remove from Tour" button (if shows have tourId)
  - "Export" button
  - "Delete" button (with confirmation)

Show Already in Tour:
- If show.tourId is not null and user tries to add to different tour:
  - Warning: "This show is already part of [Tour Name]. Move it to [New Tour]?"
  - Options:
    - Cancel
    - Move (reassign tourId)
- If show is added to tour while in tour filter:
  - Show remains visible (tour context is active)

UI Enhancements:
- Right-click context menu (power users):
  - Add to Tour
  - Remove from Tour
  - Edit
  - Duplicate
  - Cancel
- Mobile:
  - Long-press for context menu

EDGE CASES & VALIDATIONS
================================================================================
1. User tries to create second entity:
   → Backend returns 409 Conflict
   → Frontend shows error: "You already own an entity"

2. Promoter tries to access /touring:
   → Frontend hides link
   → Backend returns 403 Forbidden

3. Member tries to create show:
   → Frontend disables button
   → Backend returns 403 Forbidden

4. Invite accepted by wrong entity type:
   → Validation fails
   → Error: "This invite requires a [type] account"

5. Show added to tour while already in tour:
   → Warning modal
   → User confirms move or cancels

6. Trial expires:
   → User can still view/edit existing shows
   → Cannot create new shows beyond limit
   → Upgrade prompt appears

7. Show cancelled:
   → Both parties notified
   → Show-specific chat archived (optional: delete with warning)
   → Show remains in database (status = cancelled)

8. Tour deleted:
   → All shows in tour have tourId set to null
   → Shows become standalone
   → Confirmation warning

9. User with no entity visits /invite/{token}:
   → Redirected to sign in
   → Then redirected to onboarding (type enforced)
   → On completion: invite accepted, contact created

10. Expired invite visited:
    → Error: "This invite has expired"
    → Option to request new invite
